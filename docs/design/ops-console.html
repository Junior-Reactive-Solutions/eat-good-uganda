Design proposal · Admin surfaces · 18 Sep 2026

Eat Good Ops Console

A rework of the Super Admin and Bakery Admin interfaces around one idea: an operator should open the app and immediately see what needs doing — not a wall of totals. Same tokens, same icon set, same tenancy rules. Different information design.

2 consoles 8 screens 0 new brand colours 1 new dependency (icons) WCAG 2.1 AA held

What's costing operators time today

Observed while testing the live consoles this week.

Blocks
You can't tell where you are Nav items are <button onClick={navigate}> with no active state and no aria-current. Nothing highlights. You also can't middle-click a nav item to open it in a tab.
Blocks
The header shows a UUID instead of the bakery "Bakery ID: 1b61bf47-caa5-44b1-8a93-709485a3b99b" is debug output in the primary chrome. A baker does not know their tenant UUID and should not have to.
Blocks
Super Admin's header says "Admin Dashboard" on every page It is hardcoded. On /bakeries/:id it still says Admin Dashboard — no breadcrumb, no page title.
Slows
The dashboard answers a question nobody asked Four equal-weight totals, then three charts. Nothing says "3 orders are waiting on you" — which is the entire job of a bakery dashboard at 7am.
Slows
Tables can't sort, filter, or act in bulk Approving five bakeries means five round-trips. No sticky header, no column sort, no saved views, no row actions, no result count.
Slows
No global search Finding order EGU-2419 or a bakery by name means navigating to the right list first.
Polish
Empty states are a dead end "No orders found — Try adjusting your filters" with nothing to click, even when the real answer is "you have no orders yet, here's how to get your first one".
Polish
Settings is one 16-field scroll No sections, no sticky save, no dirty-state warning. You can navigate away mid-edit and lose everything.

What does not change

The proposal is constrained by these. Nothing below is up for negotiation.

  • ✓The palette. Every colour here comes from platform-theme.css — #c97c2d primary, #faf8f4 ground, #e2d5c3 borders. No new brand hues.
  • ✓WCAG 2.1 AA. 4.5:1 body text, 3:1 UI boundaries, 44×44px touch targets, visible focus rings, status never carried by colour alone — every pill pairs a dot, a label and a hue.
  • ✓The icon system. Existing IconAdmin* / IconNavigation* components. No second icon library.
  • ✓Tenant isolation. Bakery Admin still sees only its own bakery_id. The UUID moves out of the header into the account menu — it is still one click and one copy away for support.
  • ✓Admin apps stay platform-branded. Per 06-THEMING.md, bakery theming applies to /b/:slug/* on the storefront only — never to admin chrome.
  • ✓The stack. TypeScript, Tailwind against the same tokens, existing Button/Card/Input primitives extended rather than replaced. No UI kit, no CSS-in-JS.
  • ✓Semantic HTML first. Real <nav>, <table> with <th scope>, <label> on every input, ARIA only where HTML runs out.

Why a board

The same three orders in the current table take three clicks each to advance

Today

  • A table with status filter tabs. Advancing an order means open detail → change a select → save → back.
  • No sense of time pressure: an order placed 42 minutes ago looks identical to one placed 4 minutes ago.
  • Empty state reads "No orders found / Try adjusting your filters" even when there are simply no orders.

Proposed

  • Board mirrors the real order_status enum. Each card carries one primary advance action — Confirm, Start preparing, Mark ready — so the common path is a single tap.
  • Waiting timers turn amber then red. The oldest unconfirmed order also gets a ring, so it reads without parsing text.
  • Table view stays, one toggle away, for searching and exporting. The view persists in the URL.
  • Invalid transitions never render — the API already returns 422 for those, so the UI stops offering them.

Foundation 01

The icon set

There are 45 hand-drawn icons in components/icons/ today across six categories. They work, but stroke widths drift inside a single glyph (2px, 1.5px and 1px with opacity fades in IconProductBreadLoaf alone), and every new icon is a hand-authoring job. Here's what I'd adopt instead, and what I'd keep.

Phosphor IconsRecommended

1,512 glyphs × 6 weights ≈ 9,000 icons. Rounded terminals and a softer geometry than the technical sets — which suits a bakery far better than Tabler's squarer strokes — while still being precise enough for dense admin tables.

Package
@phosphor-icons/react
Licence
MIT. No attribution, no per-seat fee, redistribution fine.
Props
size, color, weight, alt, mirrored — plus an IconContext.Provider for defaults.
Why it fits
That prop list is almost exactly the existing IconProps contract (size / color / state / alt / data-testid). The <Icon> wrapper and every call site survive untouched — only the SVG children change.
Bonus
The weight axis solves the active-nav problem from the top of this deck: regular for idle, fill for the current page. No second icon file, no opacity hack.

Why not Flaticon

  • Attribution is legally required on the free tier — one credit line per author, visible on every screen or in the app's credits. Flaticon icons come from many different authors, so that's several credit lines in a commercial product's footer, forever.
  • Style drifts per author. Because each icon is drawn by a different designer, a set assembled from Flaticon has inconsistent stroke weights, corner radii and optical sizing — the exact problem the current hand-drawn set already has.
  • No React package. They're downloads, not a tree-shakeable dependency. You'd hand-manage SVG files, lose type safety, and ship every icon whether used or not.
  • Per-icon licence risk. Licence terms can differ by icon and by author, which is a poor foundation for a platform that will onboard paying tenants.
  • Premium clears the attribution requirement (~$8/mo) but fixes none of the other three.

The gap no library fills

Phosphor covers bread, cake and coffee. It does not cover mandazi, chapati, rolex, samosa or matoke — and neither does Tabler, Lucide or Material, because East African staples aren't in any Western icon set. That's the real argument for keeping a custom pipeline: not to redraw settings and search, but to draw the twelve things that are actually specific to selling baked goods in Kampala.

One weight per job

Six weights is only an asset if each one means something. These are the rules I'd write into the style guide.

regular The defaultNav items at rest, table row actions, form field adornments, anything inline with text.
fill Current stateThe active nav item, a selected filter, a favourited bakery. Reads instantly against its regular siblings.
bold Emphasis at small sizesStatus pills at 11px, the alert dot on a notification bell, severity marks in the action queue.
duotone Empty states onlyThe 42px illustration in "No orders yet". Never inline — it's decorative, so it ships aria-hidden.
✓

The migration is a swap, not a rewrite. Of the 45 existing icons, 34 are generic (navigation, interaction, admin, most product glyphs) and become Phosphor re-exports behind the same component names — zero call-site changes.

The 11 that stay hand-drawn are the ones that carry real meaning no library has: IconPaymentMomo, IconPaymentAirtel, IconPaymentCod, IconPaymentBank (brand marks you should not substitute), IconDeliveryBoda, and the Ugandan product glyphs above. <Icon>, IconProps, the size/color/state variants and every data-testid survive intact, so the existing icon tests keep passing.

Foundation 02

Keyboard shortcuts

Both consoles are tools people sit in all day, so they should be drivable without a mouse. The map below avoids every browser-reserved combination by leaning on single keys and sequences — the Gmail/Linear pattern — rather than piling more onto Ctrl.

Globalanywhere

  • ⌘KCommand palette — jump to any bakery, order number or page
  • /Focus search
  • ?Show this cheat sheet
  • EscClose overlay, clear selection, cancel edit
  • ⌘ZUndo the last status change (30-second window)

Go topress g, then…

  • gthendDashboard
  • gthenoOrders
  • gthenmMenu (bakery admin)
  • gthenbBakeries (super admin)
  • gthensSettings
  • gthenpPayments

Lists & tablesrows focused

  • jkMove down / up (arrows work too)
  • EnterOpen the focused row
  • xSelect the focused row
  • fOpen filters
  • rRefresh the data

Orders boardcard focused

  • 1–5Move to that stage — the column numbers are printed in the headers
  • cConfirm the focused order
  • pPrint the run sheet (no override — real print)
  • ⌘ZUndo — every stage change toasts with an undo

Menubakery admin

  • nNew product
  • tToggle availability on the focused product
  • eEdit the focused product

Formswhile editing

  • ⌘EnterSave and stay
  • ⌘SSave — a deliberate override of Save Page, because people reach for it in a form with a save bar
  • EscDiscard (prompts if there are unsaved changes)

Left alone on purpose

These belong to the browser and the operating system. Overriding them breaks muscle memory and, for the assistive-tech ones, breaks access outright.

One caveat on ⌘K: Chrome and Firefox map it to "search from the address bar". Because focus is inside the page, preventDefault() wins, and it's the convention every comparable tool uses — Slack, Linear, Notion, GitHub, Stripe. Worth knowing it's an override rather than free real estate.

✓

WCAG 2.1.4 "Character Key Shortcuts" is an AA criterion, and single-key shortcuts trigger it. Because this map uses bare letters, the implementation has to satisfy at least one of: remappable, disableable, or active-on-focus only.

The plan: Settings → Accessibility → "Single-key shortcuts", on by default, switchable off — which also protects speech-input users, for whom stray dictated letters would otherwise fire actions. Three further rules: nothing fires while focus is in an input, textarea, select or contenteditable; ? opens a discoverable cheat sheet; and every shortcut has a visible UI path, so no function is keyboard-exclusive (WCAG 2.1.1).
